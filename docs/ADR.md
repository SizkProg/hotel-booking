# Архитектурные решения

## ADR-001. Локальная сага вместо глобальной транзакции
Две независимые H2 не участвуют в XA. PENDING сохраняется перед HTTP-вызовом, завершение — отдельной транзакцией. Флаг compensationRequired служит очередью повторного освобождения. Компромисс: требуется постоянная БД и восстановление незавершённых саг для производственного режима.

## ADR-002. Интервалы и сериализация на номере
AVAILABLE означает исправность. Занятость определяется слотами с start < other.end и other.start < end. PESSIMISTIC_WRITE на Room сериализует операции confirm/release для одного номера, сохраняя параллелизм разных номеров. Слоты являются локальной проекцией бронирований Hotel, иначе корректно проверить даты при недоступности Booking невозможно.

## ADR-003. Повторные запросы и отмена
UUID брони используется как идентификатор слота. Повторное подтверждение с тем же UUID не создаёт второй слот и не увеличивает счётчик номера.

При освобождении слота запись об отмене сохраняется, даже если подтверждение ещё не пришло. Это нужно из-за тайм-аутов: запрос мог задержаться в сети и дойти до Hotel уже после отмены. По записи об отмене Hotel отклонит такой запрос. Поэтому отменённые слоты пока не удаляются из базы.

## ADR-004. Безопасность
JWT проверяется каждым бизнес-сервисом, Gateway передаёт Authorization. USER получается только регистрацией, ADMIN назначается администратором. Внутренние вызовы используют отдельный секрет и не публикуются Gateway. В промышленном режиме предпочтительны асимметричные JWT/JWK и mTLS.

## Схема БД
Booking: users(id PK, username UNIQUE NOT NULL, password BCrypt, role); bookings(id UUID PK/requestId, user_id, room_id, start_date, end_date, status, created_at, compensation_required, auto_select, requested_room_id).

Hotel: hotels(id PK, name, address); rooms(id PK, hotel_id, number, available, times_booked, version); slots(id UUID PK/requestId, room_id, start_date, end_date, released). Поля ссылок представлены числовыми идентификаторами; межсервисных FK нет. Внутрисервисные связи контролируются бизнес-логикой, физические FK не объявлены. Пароли не сериализуются в API. Нет связи JPA между базами.
